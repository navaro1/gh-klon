### 2.2 What `GIT_TRACE2_PERF` showed

The first `git status --porcelain` in a fresh klon of the 100k fixture spent
its time like this. The numbers come from a run under host load, so read the
shares, not the absolute values.

| Region | Time | What it did |
|---|---|---|
| `do_read_index` | 36 ms | read 100001 entries, index version 2 |
| `index:preload` | 76 ms | 100001 `lstat` calls over threads |
| `index:refresh` | 8 ms | `sum_lstat:0`, `sum_scan:0`: no file was re-hashed |
| `status:worktrees` | 5 ms | |
| `status:index` | 13 ms | the index against `HEAD` |
| `status:untracked` | **246 ms** | `read_directory` over the whole tree |
| rest | 7 ms | |

The `refresh` line proves that `core.checkStat=minimal` plus the fresh index
mtime already worked: git re-hashed nothing. The cost sat in one place, the
untracked scan, and the counters named the reason:

```
....directories-visited:1001
....paths-visited:101004
....node-creation:1000
....gitignore-invalidation:3
....directory-invalidation:0
....opendir:1001
```

`node-creation:1000` with `directory-invalidation:0` means that the untracked
cache held no directory node at all. Git built 1000 nodes from nothing and
opened all 1001 directories. The second `git status` printed the same three
numbers, so the scan of the first call was thrown away, not reused.

### 2.3 Why the cache never persisted

`add` already wrote `core.untrackedCache=true` into the shared config and
already ran one `git status --porcelain` to warm the cache. The index in the
klon carried a `UNTR` extension, but only a 200-byte stub: the root node and
no children.

git 2.34.1 explains it. In `dir.c`, `read_directory` ends with:

```c
if (force_untracked_cache < 0)
        force_untracked_cache = git_env_bool("GIT_FORCE_UNTRACKED_CACHE", 0);
if (force_untracked_cache &&
    dir->untracked == istate->untracked &&
    (dir->untracked->dir_opened ||
     dir->untracked->gitignore_invalidated ||
     dir->untracked->dir_invalidated))
        istate->cache_changed |= UNTRACKED_CHANGED;
```

On this git version the write-back decision reads the environment variable
`GIT_FORCE_UNTRACKED_CACHE` and nothing else. `core.untrackedCache=true` makes
git *build* the cache on every index read (`tweak_untracked_cache` calls
`add_untracked_cache`), and that first creation marks the index dirty once, so
the stub reaches the file. Every later call finds the stub already there,
creates no new cache object, marks nothing dirty, and drops the whole scan on
exit. Later git versions also derive `force_untracked_cache` from the config
key; git 2.34.1 does not.

The measurement that settles it: one `GIT_FORCE_UNTRACKED_CACHE=1 git status
--porcelain` grew the index from 8031353 to 8074491 bytes, and the next
ordinary `git status --porcelain` reported `node-creation:0`, `opendir:0`, and
an untracked step of 12 ms instead of 271 ms.

## 3. The change

Two lines of behaviour, in `src/cli/add.rs` and `src/warm.rs`, plus one helper
in `src/git.rs`.

1. **`add` warms the cache with `GIT_FORCE_UNTRACKED_CACHE=1`.** The warming
   `git status --porcelain` that `add` already ran now persists its scan.
2. **The warm process warms it once more when the last ignored directory
   lands.** `add` returns before the background copy renames `build/` into
   place (C12, R36). That rename changes the mtime of the klon root, which
   invalidates the root node of the cache, and git 2.34 never writes the repair
   back. One forced status at the end of `warm::run` leaves a cache that
   matches the finished tree. A failure there is dropped: it costs one reopen
   of the root, never the klon.
3. **`git::run_env`** runs a `git` command with extra environment variables.
   `git::run` now calls it with an empty set, so there is one implementation.

Effect on the counters of the first `git status` in a fresh klon, after the
warm landed:

```
....directories-visited:1001
....paths-visited:1000
....node-creation:0
....gitignore-invalidation:0
....directory-invalidation:0
....opendir:0
```

## 4. Permitted changes that this report rejects

The goal permitted four other levers. Each was measured and left alone.

- **`index.version=4`.** The key is already in the shared config, and it does
  nothing for a klon: `add` copies golden's index file, so the klon inherits
  its version 2 bytes, and git keeps the version of an index it read. Forcing
  the conversion with `git update-index --index-version 4` shrank the file from
  8074491 to 7264417 bytes and moved the index read from 42 ms to 45 ms, that
  is, nowhere outside the noise. It would add a full 100k index write to every
  `add`. Not taken.
- **`core.checkStat=minimal` and the fresh index mtime.** Already correct. The
  trace proves it: `refresh/sum_lstat:0` and `refresh/sum_scan:0` on the first
  call, so no file was opened or re-hashed.
- **The index copy.** Already correct. Nothing in the trace pointed at it.
- **`index.threads`.** Writing the `IEOT` extension needs the key set when the
  index is written. The one A/B pair landed in a load spike (39 runnable tasks)
  and gave no readable answer. The index read is 42 ms of a call that already
  passes both limits, so this stays unexplored rather than half-measured.
- **`core.fsmonitor=false`.** Skipped on purpose. The default is already off,
  and `ensure_config` writes to the shared config, so setting it would also
  turn off a deliberate fsmonitor in golden. That is a policy change, not a
  status fix.
- **`status.aheadBehind=false`.** The bench times `git status --porcelain`,
  which prints no ahead/behind line and computes none. No effect to win.
