## 2. What this change does

`git checkout -q --force <branch>` does three jobs in a klon: it writes the
working-tree files that differ between the spare's commit and the branch, it
replaces the index with one that matches the branch, and it moves `HEAD`. G1
traced the cost: of 355 ms inside that one process, 347 ms are
`do_write_index` and 345 of those are the cached-tree write. git rewrites the
whole index, 7 MB of it here, although the branch changes 22 paths of
100,001.

`src/splice.rs` does the same three jobs without that rewrite. It runs only on
the spare-served path, and **a splice that is not certainly correct refuses**;
the refusal falls back to the same `git checkout` every klon ran before, and
`KLON_DEBUG=1` prints the reason.

### 2.1 The files: git writes them, through a small index

One `git diff-tree -r -z --raw --no-renames <spare commit> <branch>` names
every path that differs, with the mode and the object id the branch holds. The
splice writes a temporary index of version 2 that carries only those entries,
then runs

    GIT_INDEX_FILE=<admin>/index.klon-splice git checkout-index --force --all

git itself writes those files. That keeps every rule of a real checkout — the
`.gitattributes` conversions, `core.autocrlf`, symbolic links, the executable
bit and the umask, a file that replaces a directory — inside git, where they
are already right, and it reads 22 entries instead of 100,001. Writing the
blobs by hand with `git cat-file --batch` would have saved that git process,
which §3.2 measures at 20.6 ms together with the removals, and would have
needed klon to reimplement every one of those rules; a filter klon did not know
about would have produced a wrong working tree in silence.
The paths the branch drops go by hand, after that call: one `unlink`, then
`rmdir` up the parents while they come away empty, which is what
`unlink_entry` and `remove_scheduled_dirs` do.

### 2.2 The index: the untouched entries keep their bytes

`splice::plan` walks the entries of the spare's index once and emits a new
one. An entry the branch leaves alone is copied byte for byte, in runs, so
all but the 22 the branch touches move as a handful of `memcpy` calls. An entry
the branch changes is written again from the diff record, and its stat fields
are filled from an `lstat` of the file `checkout-index` has just written, so
`git status` compares and does not re-hash. An added path is inserted in
order; a dropped path is left out.

Index version 4 spells each path against the previous one, so an entry may be
copied only while the entry before it is still the entry that was there. The
walk tracks that, and re-spells the one or two entries around each change.
Version 4 is not refused: `ensure_config` sets `index.version = 4`, so it is
the version every index klon makes, and refusing it would have meant refusing
the common case. Versions 2 and 3 are copied the same way and need no
re-spelling at all.

### 2.3 The extensions

| Extension | What the splice does | Why |
|---|---|---|
| `TREE`, the cached tree | **dropped** | A stale cached tree makes `git commit` write a wrong tree. Patching it means re-emitting a recursive structure, and a bug there is silent and severe. git treats a missing cached tree as "nothing cached" and rebuilds it from the entries, which are the truth. The price is measured, not guessed: the first `git write-tree` in a spliced klon takes 0.76 s against 0.04 s in a klon `git checkout` made, and every one after it takes 0.04 s, because that first call writes the cached tree back. Both calls answer the same tree, `2a27630…`, which is `feature^{tree}` (§4.8). The cost is off the `add` path and lands on whoever commits first. §3.3 keeps the alternative on the list with that price on it. |
| `UNTR`, the untracked cache | **kept, with its location rewritten** | The identity string names the worktree, and git drops the whole cache on a mismatch (G1 §3.2). The splice does that rewrite in the same pass, which is why step 6 of `add` no longer reads and writes the index on its own. |
| `IEOT`, the entry offset table | **recomputed** | Its blocks are byte offsets of entries, which a splice moves. Dropping it would cost every later git command the threaded index read that G2 turned on (18 ms against 38 ms). |
| `EOIE`, the end of index entries | **recomputed** | It holds the offset where the entries end and a hash over the extension headers, and a splice changes both. |
| anything else | **refuses** | `REUC` and `FSMN` carry state a splice would leave stale, and `link` (split index) and `sdir` (sparse index) are not ignorable at all. |

The trailer is a SHA-1 over the whole spliced buffer, which git verifies on
every read and `git fsck` checks again.

### 2.4 `HEAD`

`git symbolic-ref -m "checkout: moving from <old> to <branch>" HEAD
refs/heads/<branch>`. The message is the one `git checkout` writes, so
`git checkout -` and `@{-1}` read the reflog of the klon the same way.

### 2.5 What must be true before the splice looks at anything

A `git checkout --force` rewrites every path that differs, so it needs no
promise about the tree it starts from. A splice keeps the bytes of every path
the branch leaves alone, so it needs three, and each is a recorded fact, not a
guess:

| Rule | What it stops |
|---|---|
| `index_matches_head` (G1) | A staged change makes the spare's index differ from `head` in a way that a diff between two commits cannot name, so the splice would keep an entry the branch does not hold. |
| `tracked_clean` (new here) | The status the builder runs inside the spare named no tracked path, so the files of the spare match the index it carries. Without it a file that golden had edited would stay edited in the klon and `git status` would print it. The test `a_spare_that_does_not_match_its_index_falls_back_to_git_checkout` fails without this rule. |
| `shared_ignore_hash` (G1) | Kept for the same reason G1 kept it. The splice writes only tracked paths, so this guards the recorded lists beside it, not the splice; it costs nothing and it keeps the two shortcuts under one rule. |

One more thing must be true, and it is about the repository, not the spare:
`git checkout` runs the `post-checkout` hook and the splice runs no hook at
all, so a repository that has an executable one keeps the real checkout. The
check is one `git config --get core.hooksPath` and one `stat`, inside the
`index` step of the per-step lines.

`splice::plan` then refuses, on the bytes themselves: an index it cannot
parse, an extension it does not know, an entry at a merge stage or with an
assume-valid or extended flag, a submodule anywhere in the index, a SHA-256
index, a diff above 1000 paths, a diff that changes a `.gitattributes`, a diff
that names a submodule, a mode it does not write, and a drop of a path the
index does not hold.

### 2.6 The order of the two file jobs, and the defect that set it

**The first version of this change deleted a file outside the klon.** The
review found it, it is the worst defect this work produced, and a reader of
this report should see it in full.

The splice wrote the paths the branch holds first, with `git checkout-index`,
and removed the paths the branch drops afterwards. Take a branch that replaces
a tracked directory with a symbolic link of the same name:

- `main` holds the tracked file `keep/keep.txt`, so `keep` is a real directory.
- `feature` holds `keep` as a symbolic link to a directory outside the klon.
- `git diff-tree` names two changes: `D keep/keep.txt` and `A keep`.

In that order, `git checkout-index` installed the link first. The removal of
`keep/keep.txt` then resolved `keep` through the new link and deleted
`<somewhere else>/keep.txt`. The path klon handed to `unlink` was inside the
klon; the file it reached was not. That is the same class of escape that the
four rules of G1 §3.7 guard the path fixup against, and this change had opened
it again on the checkout side.

The same order also broke every swap of a file and a directory: writing a file
where a directory still stood, or a directory where a file still stood, met
`EISDIR` or `ENOTDIR`.

**The fix is the order.** The removals now run first. At that moment the
working tree is still the one the spare's index describes, and the index cannot
hold both `keep` and `keep/keep.txt`, so `keep` is a real directory and the
path resolves where it says. `git checkout-index` then creates whatever shape
the branch wants over a tree that no longer holds the old one, and git's own
`--force` handling settles the rest. Two tests hold this,
`a_branch_that_replaces_a_tracked_directory_with_a_symlink_deletes_nothing_outside`
and `a_branch_that_swaps_a_file_and_a_directory_is_checked_out_whole`, and both
fail with the order the review found.

The lesson for the next reader: a splice writes paths that a diff names, and a
diff names paths in a tree that the writes themselves change. Do the work that
shrinks the tree before the work that grows it.

### 2.7 One `git diff-tree` instead of two

The recorded lists of G1 and the splice both need the same diff. `add` runs it
once, as `--raw`, so the record names the modes and the object ids too. On the
100k fixture that call costs 29 to 43 ms, which is not a price to pay twice.

`KLON_NO_SPLICE=1` turns the whole thing off and `add` runs `git checkout` as
it did before. The differential test uses it.

## 3. Where the rest of the time goes

The splice removes the checkout, which G1 measured at 62 to 65 % of the `add`
transaction. It cannot remove the other 35 %, and the 100 ms line needs all of
it. This section names every remaining step with its cost, so the next goal
starts from a list and not from a guess.

### 3.1 The steps, before and after

Two `add` calls on the same 100k fixture, minutes apart, both spare-served,
both checking out the same commit with the same 22 changed paths. The first
runs with `KLON_NO_SPLICE=1`, which is the `git checkout` path every klon took
before this change. The host carried other agents' builds; the loads are named
above each column (§4.4 holds the two blocks verbatim).

| Step | `git checkout`, load 19.4 | splice, load 17.5 | What it is |
|---|---|---|---|
| `resolve-and-probe` | 40.7 ms | 23.7 ms | the worktree list, the config, the backend probe |
| `plan` | 0.5 ms | 0.6 ms | skipped for a spare (G1 §3.1) |
| `register` | 37.7 ms | 23.7 ms | `git worktree add --no-checkout --detach --lock` |
| `claim` | 12.4 ms | 13.0 ms | two renames under the spare lock |
| `index` | 98.1 ms | 25.8 ms | before: read 7 MB, relocate, write 7 MB. after: read only; the splice writes once |
| `config` | 13.7 ms | 7.7 ms | `ensure_config` and the shared ignore hash |
| `checkout` + `fixup` | 850.6 ms | 176.7 ms | one `git diff-tree`, then the checkout or the splice beside the path fixup |
| `hooks` | 32.4 ms | 15.2 ms | the per-tree hook copy (C22) |
| `env` | 2.1 ms | 2.0 ms | the envelope file |
| `hooks-export` | 10.4 ms | 7.3 ms | the worktree-config check (C22) |
| `clean` | 0.0 ms | 0.0 ms | the recorded list is empty (G1 §3.3) |
| `unlock` | 13.6 ms | 9.6 ms | `git worktree unlock` |
| `spare-start` | 6.1 ms | 4.5 ms | the detached builder |
| **the transaction** | **1118.3 ms** | **309.8 ms** | the sum of the lines above |
| the wall time | 1.71 s | 0.73 s | `/usr/bin/time` also counts the `gh` wrapper, about 0.32 s (G1 §5.2) |

Inside the parallel block the two sides now cost almost the same: the splice
147.9 ms and the path fixup 138.6 ms, with 28.8 ms of `git diff-tree` in front
of them. **The path fixup, not the checkout, is what a further goal has to
attack.**

### 3.2 Inside the splice

| Part | load 17.5 | What it is |
|---|---|---|
| `splice-plan` | 66.4 ms | the walk over 100,000 entries and the new buffer |
| `splice-files` | 17.1 ms | `git checkout-index` for the 22 paths, and the removals |
| `splice-checksum` | 28.5 ms | the SHA-1 over the 7 MB the splice wrote |
| `splice-write` | 24.1 ms | the write and the rename of the index |
| `splice-head` | 8.6 ms | `git symbolic-ref` |
| the whole splice | 147.9 ms | |

The checksum is the one part git would also pay: it hashes the index it writes
too. The `sha1` crate carries an x86 backend with runtime SHA-NI detection, so
28.5 ms over 7 MB is the host's load, not a software fallback.

### 3.3 The levers this session measured and did not spend

| Lever | What it would save | Why it stayed |
|---|---|---|
| more workers on the path fixup | up to about 130 ms | The fixup now sets the pace of the parallel block. It walks the 20,000 files of `build/` over four workers, and `WORKERS = 4` is the measured optimum of the clone walk (handoff §4). Raising it changes the clone path too, needs its own measurement, and belongs to a goal about the fixup, not about the checkout. |
| `git diff-tree` on its own thread | about 29 ms | It could start at the claim and finish behind the index read. That is one more thread inside the `add` transaction, for a step whose removal does not reach the goal. |
| `index.skipHash` | the whole 28.5 ms checksum | git 2.40 and later. The host and the CI floor are 2.34.1 (G1 §4). |
| writing `<admin>/HEAD` by hand | about 9 ms | Spec §5: klon shells to git for every repository state change. The rule wins over the milliseconds. |
| `hooks` and `hooks-export` beside the splice | about 22 ms | Both must run before the envelope write, so that an `add` that dies between them leaves no half-made klon. Moving them needs that ordering re-argued. |
| a second index write to let `git checkout-index` update the stat data | — | It would let git fill the stat fields instead of klon, but `git checkout-index -u` rewrites the whole index, which is the cost this goal removes. |

### 3.4 The 100 ms line

It is not reached, and the arithmetic says why. Take the splice column of
§3.1 and remove everything a further change could plausibly remove inside this
goal's scope: the diff-tree thread (29 ms) and the hooks (22 ms) leave about
259 ms. The path fixup alone is 139 ms of that, and the two git processes that
`add` cannot do without — `worktree add` and `worktree unlock` — are another
33 ms. A 100 ms `add` on this fixture needs the fixup to go somewhere else and
the index to stop being hashed, and the second one needs git 2.40.

### What the goal did reach

- The checkout is gone from the spare path. G1 measured it at 62 to 65 % of the
  `add` transaction; the per-step lines now show 170.1 ms of splice against
  487.6 ms of checkout in the same pair (§3.1), and the bench cell falls from
  626 ms quiet and 965 ms loaded (G1 §5.1) to PLACEHOLDER-P50 ms at load
  PLACEHOLDER-LOAD.
- The index the splice writes is the index git writes. The differential test
  compares the two through git — every entry's mode, object id, stage and path,
  the tree the index makes, the header, the extension list, and the status —
  and the bench's own check re-hashes all 100,001 entries and finds nothing.
- Every case the splice cannot be certain about falls back to `git checkout`,
  and each fallback has a test.
- The `add` path lost one `git diff-tree` and one read-and-write pass over the
  whole index, both of which the direct-clone path never paid and the spare
  path paid twice.

### Why the 100 ms line does not fall

§3.4 has the arithmetic. In short: the checkout was 62 to 65 % of the
transaction and it is gone, but the path fixup, the two `git worktree`
processes that `add` cannot do without, the backend probe, and the checksum
over the index that git 2.34 requires are the rest, and they add up to more
than 100 ms on this fixture. Two of those need work that belongs to other
tickets: a goal about the path fixup, and git 2.40 for `index.skipHash`.
