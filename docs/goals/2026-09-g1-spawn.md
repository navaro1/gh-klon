# G1 — M1 spawn on the 100k fixture with a spare

Date: 2026-09-06
Goal: spec §7 G1. Requirement: spec §3 R12.
Issue: [#38](https://github.com/navaro1/gh-klon/issues/38).

Condition: `gh klon bench --cell m1-add-100k --json` reports `p50_ms <= 1000`
with `timing_valid: true` and `spare: true` on ext4, and `p50_ms <= 200` on a
btrfs loop volume.

Host: Ubuntu 22.04, ext4 on NVMe, git 2.34.1, 20 CPUs, 62 GB RAM. Other
agents ran builds on the host during the whole session; every number below
names the one-minute load average it was taken at. The `copy` backend served
ext4; the btrfs volume is a udisks loop image made the S1 way, where the
bench fixture gets the `reflink-walk` backend.

## 2. Where the time went before this change

`KLON_DEBUG=1` prints one line per step of the `add` transaction. On the
persistent 100k fixture (100,000 tracked files over 1000 directories, 20,000
ignored files of 100 kB in `build/`, `feature` with 20 edits and 2 new
files), a spare-served `add` at `main` (commit `deaec1a`) took 3.62 s at
load 18:

```
klon: debug: add resolve-and-probe 33.8 ms
klon: debug: add plan 1739.2 ms
klon: debug: add register 21.2 ms
klon: debug: add claim 7.7 ms
klon: debug: add index 1.6 ms
klon: debug: add config 27.8 ms
klon: debug: add checkout 424.2 ms
klon: debug: add clean 361.7 ms
klon: debug: add fixup 387.8 ms
klon: debug: add hooks 14.5 ms
klon: debug: add env 2.0 ms
klon: debug: add hooks-export 6.3 ms
klon: debug: add status-warm 565.2 ms
klon: debug: add unlock 7.8 ms
klon: debug: add spare-start 3.7 ms
klon: debug: add warm-start 0.2 ms
wall 3.62 s
```

Four of those steps walked the whole tree although the spare made the
walk pointless:

| Step | What walked | Why it was there |
|---|---|---|
| `plan` (1739 ms) | the byte estimate and the warm plan of a clone: one `stat` walk over golden's 120k entries plus `git ls-files --others --ignored` in golden | R41 and R36 need them for a clone. A spare is one rename and writes nothing. C12 added this after C9 measured the spare at 1.16 s. |
| `clean` (362 ms) | `git clean -fdq`: a directory walk over the klon | golden may hold untracked files that the clone copied. The spare almost never does. |
| `fixup` (388 ms) | `git ls-files --others --ignored --directory` in the klon, then the walk over `build/` | the pass asks git for the ignored roots. The spare record already names them. |
| `status-warm` (565 ms) | the untracked scan of the first `git status`, all 1001 directories | the untracked cache had to be built from nothing. |

The checkout (424 ms) is git's own work: read the index, `lstat` 100k
entries, unpack the tree, write the index.

## 3. What this change does

### 3.1 The clone is planned only when the clone happens

`add` now asks `spare::looks_usable` before it plans. That check reads
`spare.json` and the three exclusion files; it runs no git command and takes
no lock. When it passes, the estimate, the free-space check (R41), the warm
plan (R36), and the progress line wait. When the claim then fails anyway
(another `add` took the spare in between, or the lock found it torn), `fill`
plans after the registration and a refusal rolls the `add` back through the
existing cleanup path, so the outcome is the same one process later. The
`two_concurrent_adds_use_the_spare_at_most_once` test exercises that path.

### 3.2 The spare carries its untracked cache, relocated at the claim

The lead in the brief, "run `git status` in golden before the index copy",
does not work as stated, and the reason is worth recording. git keeps the
untracked cache in the `UNTR` extension of the index, and that extension
starts with an identity string:

```
Location /home/navaro/.cache/klon/g1/golden.wt/before-1x, system Linux
```

`ident_in_untracked` in `dir.c` compares it with the worktree git runs in
and drops the cache on a mismatch. A klon moved from `before-1` to
`before-1x` went from `opendir:0` to `node-creation:1000 opendir:1001` on
its next status (§5.7). So a cache from golden, or from the spare's own
location, is dead on arrival in the klon.

The builder therefore runs the forced status *inside the spare*, with
golden's common directory as `GIT_DIR`, the spare as `GIT_WORK_TREE`, and
the copied index as `GIT_INDEX_FILE`, after it wrote the three status config
keys and the `/.klon/` exclude line. The claim then rewrites the identity:
`src/untracked.rs` walks the index entries to the extensions, replaces the
location in the `UNTR` identity, fixes the extension size (and the `EOIE`
hash when that extension is present), and writes a correct SHA-1 trailer,
which git verifies on every read. Every entry byte stays as it was; this is
not the entry splice of G4. The relocation costs one read and one write of
the 8 MB index plus one SHA-1 pass, 70 to 100 ms under load on this host
(`index` in the tables below). An index the code cannot read moves as it is,
and the first status rebuilds the cache as before.

`git checkout` keeps the extension (`move_index_extensions`) and marks only
the directories it wrote. The first status in a fresh klon then opens 21
directories instead of 1001: the 20 that `feature` edits and the root, which
gained `.klon/`. The builder that `add` starts afterwards runs one forced
status in the new klon before it clones, so the cache is written back
complete off the critical path. A status right after `add` reads
`node-creation:0 opendir:21`; one after the builder reads `opendir:0`.

### 3.3 `git clean` gets the list instead of the walk

The status that the builder runs in the spare prints the untracked paths of
the spare, and the builder records them in `spare.json` as `untracked`.
`add` passes exactly those paths to `git --literal-pathspecs clean -fdq --`
and runs no clean at all when the list is empty. A direct clone, or a spare
from an older builder, reads the list from its own status. The semantics do
not change: the paths are the ones `git status` would report, and `clean -d`
removes a fully untracked directory from its collapsed name. A list above
1000 entries falls back to the plain walk.

### 3.4 The fixup runs beside the checkout, from the recorded roots

The spare record lists the ignored directories it holds (`top_mtimes_after`,
the output of the same `git ls-files --others --ignored --directory` that the
fixup pass used to run in the klon). `fixup::run_named` starts from that
list, and since the pass touches only ignored directories and the checkout
never does, the two run on two threads and the slower one sets the pace. A
direct clone keeps the old order: the fixup asks git after the checkout and
runs beside the status.

### 3.5 No status on the critical path of a spare-served `add`

With the relocated cache and the recorded list, the inline status had one
job left: writing 21 re-read directories back. That moved to the builder
(§3.2). The direct-clone path keeps its inline forced status, which is the
G2 change (PR #77) and stays as that PR wrote it.

### 3.6 One git call fewer in the claim

The claim ran `git rev-parse HEAD` to print a debug line about a stale
spare. It runs now only under `KLON_DEBUG=1`.

## 4. The levers that were measured and left alone

| Lever | Finding |
|---|---|
| `index.skipHash` | git 2.40 and later. The host has 2.34.1; the CI floor is 2.34.1. Not available. |
| `index.threads` | Setting it to `true` and forcing an index write on git 2.34.1 produced no `IEOT` extension, so no threaded read. G2 saw the same. Not taken. |
| `checkout.workers` | Parallel checkout helps a checkout that writes many files. This one writes 22. Not taken. |
| `core.preloadIndex` | Already on by default; the trace shows `index:preload` at 57 ms over threads. |
| the journal write count | Five state writes and one delete, each a small file plus a rename with no `fsync`. They do not appear in the per-step lines above 1 ms. Not changed. |
| fewer `git config` calls | `ensure_config` reads once and writes nothing after the first `add` (C9). The remaining `git config --get` of the hooks copy and the worktree-config check cost 2 to 3 ms each on a quiet host. Not changed. |
